## 1. Dashboard Overview

The SOAR Incident Containment Engine dashboard provides a clear view of security alerts and their current incident status.

The dashboard is designed to help the user quickly understand:

* Which alert was generated.
* Where the alert originated from.
* What type of security event occurred.
* How severe the alert is.
* The reputation score of the source, when available.
* The calculated risk level.
* What action is recommended.
* Whether the recommended action has been completed.

The main dashboard fields are:

| Field                | Description                                                                     |
| -------------------- | ------------------------------------------------------------------------------- |
| `alert_id`           | Unique identifier for the security alert.                                       |
| `source_ip`          | IP address associated with the alert.                                           |
| `alert_type`         | Type of security event detected.                                                |
| `severity`           | Severity level of the alert such as Low, Medium, High, or Critical.             |
| `reputation_score`   | Reputation score associated with the source, when enrichment data is available. |
| `risk_level`         | Overall risk level assigned to the alert.                                       |
| `recommended_action` | Action recommended by the response/playbook logic.                              |
| `action_status`      | Current status of the recommended response action.                              |

---

## 2. Risk and Action Mapping

The dashboard displays the risk and response information produced by the backend and playbook workflow.

### Risk Level

The `risk_level` field represents the overall risk associated with an alert.

The dashboard uses the risk level to make the incident easier to understand visually.

* **High Risk** – Requires immediate attention and response.
* **Medium Risk** – Requires investigation and monitoring.
* **Low Risk** – Lower priority and can normally be monitored.

The risk level is displayed separately from the alert severity so that the mentor can easily identify the final risk assessment.

### Recommended Action

The `recommended_action` field represents the response action generated by the playbook.

Examples include:

* **Block IP**
* **Isolate Host**
* **Monitor User**
* **Continue Monitoring**

This allows the dashboard to show not only what happened, but also what response should be taken.

### Action Status

The `action_status` field shows the current state of the response action.

Examples include:

* **Contained** – The response action has been completed successfully.
* **Pending** – The action is waiting to be executed or confirmed.
* **Monitoring** – The incident is currently being monitored.
* **Failed** – The response action could not be completed successfully.

## 3. Mapping to Tejas's Playbook Output

The dashboard is designed to represent the output generated by Tejas's playbook workflow.

The general flow is:

**Alert → Enrichment → Risk Assessment → Recommended Action → Action Status**

The dashboard maps the playbook output as follows:

| Playbook Output               | Dashboard Field      |
| ----------------------------- | -------------------- |
| Alert identifier              | `alert_id`           |
| Source of alert               | `source_ip`          |
| Detection category            | `alert_type`         |
| Alert severity                | `severity`           |
| Threat reputation information | `reputation_score`   |
| Calculated risk               | `risk_level`         |
| Response decision             | `recommended_action` |
| Execution/result of response  | `action_status`      |

For example, if the playbook identifies a malicious source IP with a high reputation score and determines that it represents a high-risk incident, the dashboard can display:

**Risk Level:** High
**Recommended Action:** Block IP
**Action Status:** Contained

This provides a simple end-to-end view of the incident from detection through response.

## 4. Dashboard Readability Improvements

During Week 4, the dashboard layout was reviewed and polished to make the incident information easier to understand.

The following improvements were included:

* Clear dashboard heading.
* Improved spacing between sections.
* Separate summary cards for alert statistics.
* Clearly labelled incident table columns.
* Visual badges for severity and risk levels.
* Clear display of recommended actions.
* Clear display of action status.
* Reputation scores are visually differentiated based on their value.
* Basic responsive layout for different screen sizes.
* Horizontal scrolling support for the incident table on smaller screens.

The purpose of these changes is to allow a mentor or reviewer to understand the current incident state quickly without checking the backend output manually.

## 6. Current Limitations

There are some limitations in the current dashboard implementation.

### 6.1 Live Backend Data

The dashboard UI currently supports the required alert fields, but some test/demo data may still be displayed using sample values depending on the current backend integration.

The final version should use the live backend/API data when the endpoint is available and stable.

### 6.2 Reputation Score

The `reputation_score` field depends on the threat-enrichment process.

If the external reputation/enrichment service is unavailable, the dashboard may display the safe fallback value provided by the backend.

### 6.3 Action Execution

The dashboard displays the `recommended_action` and `action_status` values, but actual containment actions are handled by the backend/playbook workflow rather than directly by the dashboard UI.

### 6.4 Real-Time Updates

The current dashboard refresh mechanism may require a manual refresh depending on the final backend implementation.

Automatic real-time updates can be added later if required.
