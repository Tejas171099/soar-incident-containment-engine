# Week 4 QA Plan – Dashboard

## Project

**SOAR Incident Containment Engine**

## Role

**Dashboard / QA / Documentation**

## Week

**Week 4 – Final Dashboard QA**

---

## 1. QA Objective

The purpose of this QA plan is to verify that the final dashboard correctly displays the incident information generated by the backend and playbook workflow.

The testing will verify:

* Alert information is displayed correctly.
* Severity is displayed correctly.
* Reputation score is displayed when enrichment is available.
* Risk level is correctly represented.
* Recommended action matches the backend/playbook result.
* Action status is displayed correctly.
* The dashboard handles enrichment failures safely.
* The UI remains readable and consistent for different risk levels.

The overall flow being tested is:

**Alert Input → Enrichment → Risk Assessment → Recommended Action → Action Status → Dashboard Display**

# 2. QA Scenarios

## Scenario 1 – High-Risk Brute Force Alert

### Test Objective

Verify that a high-risk brute force alert is correctly processed by the backend and displayed on the dashboard.

### Input

Example alert:

```text
alert_id: ALT-001
source_ip: 192.168.1.105
alert_type: brute_force
severity: High
reputation_score: 92
```

### Expected Backend Result

The backend should:

1. Receive the brute force alert.
2. Process the alert successfully.
3. Obtain the reputation/enrichment information.
4. Assign a **High** risk level.
5. Generate the appropriate response action.
6. Return the alert information to the dashboard.

Expected result:

```text
risk_level: High
recommended_action: Block IP
action_status: Contained
```

### Expected Dashboard Display

The dashboard should display:

| Field              | Expected Value |
| ------------------ | -------------- |
| Alert ID           | ALT-001        |
| Source IP          | 192.168.1.105  |
| Alert Type         | Brute Force    |
| Severity           | High           |
| Reputation Score   | 92             |
| Risk Level         | High           |
| Recommended Action | Block IP       |
| Action Status      | Contained      |

The **High** risk level should be visually highlighted so that the reviewer can immediately identify the incident as high risk.

### Pass Criteria

* [ ] Alert appears on the dashboard.
* [ ] Alert ID is correct.
* [ ] Source IP is correct.
* [ ] Severity is shown as High.
* [ ] Reputation score is displayed correctly.
* [ ] Risk level is High.
* [ ] Recommended action matches backend output.
* [ ] Action status is displayed correctly.

# 5. Scenario 4 – Enrichment Failure

## Test Objective

Verify that the system handles an external reputation/enrichment service failure safely.

This test confirms that a failure in the enrichment service does not cause the dashboard or backend workflow to fail completely.

### Input

Example alert:

```text
alert_id: ALT-004
source_ip: 45.33.32.156
alert_type: suspicious_activity
severity: High
```

Simulate an enrichment failure by using one of the following test conditions:

```text
Invalid API key
OR
External enrichment service unavailable
OR
Network connection unavailable
```

### Expected Backend Result

The backend should:

1. Receive the alert successfully.
2. Attempt to obtain enrichment information.
3. Detect that the enrichment service is unavailable.
4. Handle the failure safely.
5. Apply the configured fallback behavior.
6. Continue processing the alert instead of crashing.

Expected behavior:

```text
Enrichment Status: Failed
Fallback: Applied
Risk Assessment: Safe fallback behavior
Dashboard: Alert remains visible
```

The exact fallback score/risk value should match the backend implementation defined for the project.

### Expected Dashboard Display

The dashboard should:

* Continue displaying the alert.
* Not crash or become blank.
* Display the available alert information.
* Display the fallback reputation/risk information if provided by the backend.
* Display the resulting recommended action and action status.
* Clearly indicate the enrichment failure if the backend provides an enrichment status field.

Example:

| Field              | Expected Value         |
| ------------------ | ---------------------- |
| Alert ID           | ALT-004                |
| Source IP          | 45.33.32.156           |
| Alert Type         | Suspicious Activity    |
| Severity           | High                   |
| Reputation Score   | Backend fallback value |
| Risk Level         | Backend fallback value |
| Recommended Action | Backend result         |
| Action Status      | Backend result         |

### Pass Criteria

* [ ] Alert is still displayed.
* [ ] Backend does not crash.
* [ ] Dashboard does not become blank.
* [ ] Fallback behavior is applied.
* [ ] Risk information is displayed according to backend fallback logic.
* [ ] Recommended action is displayed.
* [ ] Action status is displayed.
* [ ] Enrichment failure is safely handled.
